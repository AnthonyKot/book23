# Brief — Chapter 5, "Same Door, Different Verb" (API5 broken function-level authorization)

Status 2026-09-23: **incident CHOSEN — Eaton Zveare's 2025 automaker dealer-portal disclosure**
(editor's decision, switching from the register's CBORD 2022 candidate, which failed the gate as
API2; see "Rejected" below). `chapters/05-same-door-different-verb.md` drafted, 1,907 words. Nothing

## 1. Chosen incident: automaker dealer portal (Zveare, DEF CON 33, 2025)

**Mechanism sentence (from the record):** on a carmaker's dealer portal an authenticated account
that had been granted no permissions reached the administrative create-user function — the front
end hid the page by the caller's role but the server never checked it — and the function accepted
an elevated role selection, producing a "national admin" account with platform-wide access; a
lower-privileged caller invoking a higher-privileged function whose only gate was client-side is
**broken function-level authorization (API5)**.

Sources fetched and read:
- **Primary:** Eaton Zveare, "How API flaws led to admin access to over 1k USA dealers and control
  over your car", DEF CON 33 Car Hacking Village, 8 Aug 2025 — slides PDF fetched from
  media.defcon.org, text extracted. Portal invite-only, 2FA, Java backend + Angular front end
  (slide 6); registration required an invite token validated by an API the login page called, the
  form was present in the page and revealed by editing the page's own styling (7-8); the
  registration request carried the token but the server did not check it, so anyone could register
  (9); the created account had no permissions (11); a profile-update action established a session
  (12); an admin user-management page was gated only in the browser, not the server (14-15); its
  create-user function accepted a role selection and produced a national admin (16-18); the
  national admin had platform-wide access and an impersonation feature that bypassed login and 2FA
  (33-34); Zveare limited his exploration to read-only (50); timeline 26 Jan discovered / 3 Feb
  reported via VDP / 6 Feb acknowledged / 11 Feb fixes confirmed and verified, all 2025 (50).
- **Corroboration:** Zack Whittaker, TechCrunch, 10 Aug 2025,
  https://techcrunch.com/2025/08/10/security-flaws-in-a-carmakers-web-portal-let-one-hacker-remotely-unlock-cars-from-anywhere/
  — automaker unnamed, "more than 1,000 dealerships", fixed within a week of the February
  disclosure, carmaker found no evidence of prior exploitation, Zveare quote "only two simple API
  vulnerabilities blasted the doors open, and it's always related to authentication."

**Fit and handling.** The chapter opens on the first flaw (blank/unchecked invite token) in one
sentence, labelled registration/broken authentication, then centres on the second: no-permission
account → admin create-user function → server never checked role → national admin. The API5 label
is the book's; the chapter does not put it in Zveare's mouth (he frames both as "authentication").
The automaker stays unnamed. No "verb switch" occurred in the incident; the verb angle
(GET vs DELETE on one URL) is Ledger's own and is presented as such.

## 3. Ledger design (independent of the incident choice)

### Objects reused
Alice (Cedar), Dana (Cedar tenant-admin, `Role: "tenant-admin"` already in `service/model.go`),
Ben (Birch); invoices 104 and 205; `currentUser` (ch. 2); `LoadInvoiceFor` (ch. 1); `ViewFor`
(ch. 3); `/v1` read + PDF routes still live behind the loader (ch. 1); the ch. 1 route inventory
(`Routes()` in `service/app.go`).

### The bug
Ch. 1 made every handler call `LoadInvoiceFor(user, id)`. That answers "may this caller *see* this
invoice"; it says nothing about *what* the caller may do to it. Ledger's write routes reuse the
same check:

| Route | Vulnerable mode | Fixed mode |
|---|---|---|
| `DELETE /v2/invoices/{id}` | `LoadInvoiceFor` passes → row deleted (Alice can delete 104; still 404 on 205) | requires role `tenant-admin` on the invoice's tenant; Alice → 403 (see note), Dana → 204 |
| `POST /v2/admin/invoices/{id}/void` | registered with `currentUser` only; `/admin` prefix is the only "protection" | role-gated by declaration |
| `GET /v2/admin/users` (Cedar's user list) | any logged-in user → 200 | tenant-admin only |
| `GET /v1/invoices/{id}` and `/pdf` | unchanged (read) | declared `role: user` explicitly — the point is that `/v1` never had an admin prefix, so "prefix = privilege" was never true |

Same URL, different verb: `GET /v2/invoices/104` and `DELETE /v2/invoices/104` share one
authorization story in vulnerable mode. The ch. 3 `PATCH /v2/invoices/{id}` (Reference only) stays
`role: user`; it is the decoy that *looks* like a write an ordinary user should not have.

### Repair: declared authorization per route
`service/authz.go`: `type Route struct{Method, Pattern string; Access Access}` where `Access` is
one of `Public`, `User`, `TenantAdmin` — no zero value allowed; `register()` panics (in tests) on
a route whose `Access` is unset, and `TestEveryRouteDeclares` walks `Routes()` and fails on any
route missing a declaration. Middleware `requireAccess(access, next)` runs *before* the handler,
after `currentUser`. Tenant scoping stays in `LoadInvoiceFor`; role is checked by the middleware;
the handler does neither by hand. Response for wrong role: **403** (there is nothing to hide —
the invoice's existence is already known to a tenant user through GET), unlike the ch. 1 404 for
cross-tenant; the chapter says why the two differ.

Why the local fix is insufficient: putting `if user.Role != "tenant-admin"` inside the DELETE
handler repeats ch. 1's original mistake; the next admin route copied from a user route will not
have it. The declaration makes the absence greppable: `grep -n "Access:" service/routes.go`
must list every route.

### Second path (reuses ch. 3's `PATCH /v2/users/me` repair)
Ch. 3 closed self-promotion through `ProfilePatch{DisplayName}`. Ch. 5's second path: the
admin route `PATCH /v2/admin/users/{id}` (Dana sets a Cedar user's role) is registered under the
`/admin` prefix and, in vulnerable mode, reachable to Alice — so the mass-assignment door ch. 3
shut reopens through a different route: Alice sends `{"role":"tenant-admin"}` for her own user
ID. Fixed mode: `TenantAdmin` declaration → 403, record unchanged. This is the near-identical pair
with `PATCH /v2/users/me` (typed, `User` access, safe).

### Ch. 8 dependency
PLAN §3 row 8 reuses "the prefix check from ch. 5" (case-insensitive path bypass). With the
declared-access design there is **no prefix check to bypass** in fixed mode — the vulnerable mode
of ch. 5 has one (`strings.HasPrefix(r.URL.Path, "/v2/admin")` → require admin), and that is the
thing ch. 8 can show as `/v2/Admin/...` slipping past. Record in ch. 8's brief that the prefix
check exists only in ch. 5's vulnerable mode.

### Exercise-case matrix (→ `service/ch05_test.go`, both modes)

| Case | Route | Caller | Request | Vulnerable | Fixed |
|---|---|---|---|---|---|
| A (decoy, safe) | `PATCH /v2/invoices/104` | Alice | `{"reference":"PO-9"}` | 200, reference set | 200, reference set (`User` access is correct) |

absent one) → response and whether the row changed.
