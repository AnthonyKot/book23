## Mechanism sentence and class fit

SwissBorg's operations flow asked Kiln's Connect API (via the Kiln Dashboard) for a "deactivate
stake" transaction, and because an attacker who had harvested Kiln's cloud credentials through a
compromised engineer's GitHub token had patched the API's running pod to return, alongside the
expected transaction, a second transaction reassigning the withdrawal authority of any stake account
holding more than 150k SOL, SwissBorg forwarded what came back to its custody solution and a quorum
of its signers approved it undecoded — a consumer acting on a partner API's response as though it
were what it had asked for, which is OWASP API10 (unsafe consumption of APIs: data from a
third-party API trusted more than a request body, not validated at the integration boundary).

Class check against the alternatives: it is not SSRF (no caller-supplied URL; ch. 7), not a
supply-chain package compromise (nothing SwissBorg ran was replaced; the partner's *response* was),
and not a partner-side authorization flaw (SwissBorg's own statement: the incident occurred entirely
within Kiln's systems and SwissBorg's infrastructure was not breached — which is precisely the
API10 point). Both sides of the integration published primary accounts.

## Candidates examined and set aside (for the register)

- **Mastodon CVE-2024-23832** (GHSA-3fjr-858r-92rw, Feb 2024): `FetchRemoteResource` trusted the
  fetched object's self-reported `id` instead of the queried URL; remote-actor impersonation. Clean
  API10 fit (partner identity claim trusted); set aside because a federated peer is a weaker
  "partner" analogy for Ledger's rate feed and the advisory is thinner than Kiln's post-mortem.
  Best fallback if the panel rejects a crypto incident.
- **Descope nOAuth** (20 Jun 2023): relying apps used Azure AD's mutable, unverified `email` claim as
  identity. Good fit; set aside because the consumer failure is identity merging, not a value
  written into records, and the affected apps are unnamed.
- **Truffle Security Google OAuth** (Jan 2025): relying apps trusted `email`/`hd`; set aside because
  the record itself argues `sub` was unreliable, muddying "the consumer should have validated".
- **Payment-webhook forgery** (many write-ups): mechanism fits but no single primary disclosure of a
  named service was found in the budget.

## Handlers / functions needed in `service/`

- `pollRates` **vulnerable** (`ch10-rates-vulnerable`): `http.Get("https://rates.partner.example/latest")`
  (default client: follows redirects), `json.Decode` into `map[string]float64`, `store.rates = m`
  wholesale. `store.CreateInvoice` (same excerpt): `if r, ok := store.rates[inv.Currency]; ok {
  inv.AmountPence = round(amount * r * 100) }` — applies any key present, including `GBP`.
- `rateRow` (`ch10-rate-row`): `struct{ EUR float64 }`; decode with `DisallowUnknownFields`; band
  check `0.70 <= EUR <= 1.10`; else keep last good rate, record an Ops page (a fixture counter).
- `pollRates` **fixed** (`ch10-rates-fixed`): fetch via `egress` (no redirect following; 302 is
  returned as a result and no row stored), decode `rateRow`, band check, store `Rate{Value, AsOf}`.
  `CreateInvoice` fixed: converts only when `Currency == "EUR"` using the stored rate, and records
  `FXRate` and `AmountEUR` on the invoice; GBP invoices never consult the table.
- `POST /v2/refunds/quote` **vulnerable** (`ch10-refund-quote-vulnerable`): after `LoadInvoiceFor`
  and the ch. 6 checks, converts the requested EUR amount at `store.rates["EUR"]`.
- `POST /v2/refunds/quote` **fixed** (`ch10-refund-quote-fixed`): converts at `inv.FXRate`;
  `store.rates` is read only in `CreateInvoice`.
- Mode behaviour: vulnerable = bare `http.Get`, map decode, no band, no recorded rate, quote at
  today's rate. Fixed = all earlier repairs plus the above. The vulnerable poller must not be
  presented as coexisting with ch. 7's fixed egress (CONTEXT: controlled counterexample).
- Test injection: ch. 7's fake resolver + fake transport keyed by dialed address, returning the five
  canned responses; fake clock for `AsOf`; no network.

## Exercise-case matrix (this chapter's test, to run in both modes once the service code exists)

Poller fetch followed by `CreateInvoice` for 412 (€300.00) and 104 (£1,800.00). "Cap" = teammate's
decoy fix (reject rate > 10), framing only.

| Case | Partner response | Cap | Vulnerable build | Fixed build |
|---|---|---|---|---|
| 1 (decoy) | `200 {"EUR": 92}` | rejects | rate 92 stored; 412 = 2760000 pence (£27,600.00); 104 = 180000 | row refused (band); last rate kept; 412 = 27600 |
| 2 (baseline / pair-safe) | `200 {"EUR": 0.92}` | passes | 412 = 27600; 104 = 180000 | same, plus `FXRate 0.92`, `AsOf` recorded |
| 3 | `200 {"EUR": -0.92}` | passes | 412 = −27600 pence | row refused (band); Ops paged; 412 = 27600 |
| 4 (pair-vuln) | `200 {"EUR": 0.92, "GBP": 0.5}` | passes | 412 = 27600 correct; **104 = 90000 (£900.00)** | row refused at `GBP` (unknown field); both correct |
| 5 | `302 Location: https://rates.partner.example/v2/latest` → `200 {"EUR": 0.92}` | never sees it | redirect followed, row stored | `egress` returns 302, nothing stored, last rate kept |

## Claims to gate (checks/claims/10.tsv) — all in the chapter header comment

GitHub token of a Kiln infrastructure engineer; branches created and deleted to trigger CI; secrets
and cloud credentials harvested; payload injected into a running Kubernetes pod hosting the Kiln
Connect API; one endpoint's logic modified; malicious transaction returned in addition to the
expected "deactivate stake" transaction; withdrawal authority changed only above 150k SOL; customer
unstaked via Kiln Dashboard on 31 Aug 2025; forwarded to custody, approved by a quorum of
signatories; detection 8 Sep 2025; 192,000 SOL (SwissBorg); ~$40 million (The Block, secondary —
mark as such); Kiln "consistently recommended" decoding before signing and provides a tool;
SwissBorg declined the tool (not integrated, not open-source/verifiable, "did not meet basic
security standards"); "did not breach SwissBorg's wallet infrastructure" / "occurred entirely within
Kiln's systems"; no evidence of other affected customers.

## Not verified / deliberately omitted

- The dollar figure is not in either primary account; the chapter says "press reports put near
  forty million dollars". Drop the clause if the panel wants primary-only numbers.
- The chapter says the malicious authority change was in "a second transaction" (Kiln's wording:
  "a malicious transaction, in addition to the expected 'deactivate stake' transaction"). Secondary
  analyses (rekt.news, Halborn) describe eight `authorize` instructions inside one transaction of
  975.33 SOL with on-chain hashes; those details are omitted because they are not in the primary
  accounts. If the panel prefers the on-chain reading, the sentence "Alongside it, it returned a
  second transaction" needs rewording to "alongside the instructions it expected".
- Kiln's post-mortem says the customer's transaction was on 31 Aug and the authority was used on
  8 Sep; SwissBorg's account frames 8 Sep as Kiln's sales team contacting them about unstaking.
  The chapter uses Kiln's dating for the signing and the joint statement's for detection.
- Whether Kiln's decoding tool would have surfaced the extra instructions is not stated by either
  side; the chapter does not claim it would.
- The SwissBorg X post (first public attribution to "a partner API (Kiln)") could not be fetched;
  not cited.
- Ledger's rate feed, band, invoice 412 and the recorded-rate design are invented for the analogy
  and labelled as Ledger's; never presented as Kiln's or SwissBorg's implementation.
- Whether ch. 7's fake transport can express "302 then 200" for case 5 depends on the service build.
