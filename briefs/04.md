# Chapter 4 implementation brief — Nobody Counted (API4)

## Incident choice and fit

**Mechanism sentence (Instagram 2019, selected):** Instagram's account-recovery endpoint checked a
six-digit code and rate-limited attempts, but concurrent requests from rotating source addresses
let the researcher submit many guesses against one target — the observed limit failed to bound
the target's aggregate attempt budget, which is API4 (unrestricted resource consumption).

**Why the switch from the register's X/Twitter 2022 candidate.** The Twitter bug (HackerOne
1439026) is, at its core, an access-control / discoverability bypass, closer to API1/API3 than
API4. X later confirmed 5.4 million affected accounts, showing why repeated lookup volume matters;
the report does not establish that rate limiting was absent. API4 is a secondary reading of this
incident. Instagram 2019 is a clean, primary-sourced API4 case: the observed limiter did not bound
one target's guesses. Decision: lead Chapter 4 with
Instagram; keep Twitter as a short, clearly-labelled aside for the "limit the loud route, not the
enumerating one" point. Both have primary/near-primary sources; see claims file.

**Archived sources in resources/incidents/04/:**
- Laxman Muthiyah, "How I Could Have Hacked Any Instagram Account", thezerohack.com (primary;
  its own WordPress post metadata records 14 July 2019 publication and 19 October 2024 revision).
- HackerOne report 1439026 JSON (title "Discoverability by phone number/email restriction bypass",
  reporter zhirinovskiy, created 2022-01-01, disclosed 2022-02-11, resolved, $5,040, severity high).
  The report's impact paragraph is the API4 hook; quote it, not the reproduction steps.
- X's 2023 incident update (vendor primary source): July 2022 sale report, confirmed exploitation,

## Handlers the service needs (all new in ch. 4; reuse ch. 1–2 primitives)

- `POST /v2/auth/otp/request` — issues a 6-digit code for an account, stores a challenge
  `{account_id, challenge_id, code_hash, expires_at (10 min), attempts=0}`. Uses the fake clock;
  fixed mode refuses reissue for a locked account until that challenge's ten-minute window ends.
- `POST /v2/auth/otp/verify` — **vulnerable**: compares code, returns session (12h token from ch. 2)
  on match; only the per-IP limiter guards it. **fixed**: increments `attempts` on the challenge;
  at 5 wrong, lock the account's active challenge (subsequent verifies 423/`locked`); a correct
  code retires it; requesting a replacement cannot reset the lock during its window.
- Limiter middleware with a pluggable key function:
  - `keyPerIP(r)` → client address (the vulnerable OTP guard and route B in the exercise).
  - `keyPerChallenge(account_id, challenge_id)` → the fixed OTP budget (max 5).
  - `keyPerTenantRouteMinute(tenant, route)` → 30/min lookup budget independent of caller IP,
    wired for both v1 and v2 in fixed mode via the gateway fixture.
- `GET /v2/invoices?email=…` and `GET /v1/invoices?email=…` — lookup routes reusing
  the server-side tenant filter for authz; in vulnerable mode v2 has only an IP-keyed budget and
  v1 is not registered (the forgotten-door twist). Fixed mode registers both with the tenant-route
  budget. Both must still respect ch. 1 tenant scoping.
- `GET /v2/invoices?limit=N` — cap N at 50 in fixed mode; unbounded in vulnerable mode.
- Fake clock (shared with ch. 2) and a deterministic in-memory limiter store; no real time, no
  network, no goroutine races in tests — model "many source addresses" by varying the injected
  client IP, not by concurrency.

## Excerpt markers used by the prose

- `ch04-otp-vulnerable` — the verify handler with only the per-IP guard.
- `ch04-limiter-per-ip` — the limiter keyed on client address.
- `ch04-otp-fixed` — verify handler counting per (account, challenge), lock at 5, retire on use.

## Exercise-case matrix (→ service/ch04_test.go, both modes)

| Case | Route | Caller / input | Sequence | Vulnerable build | Fixed build |
|---|---|---|---|---|---|
| A | `POST /v2/auth/otp/verify` | Ben's account, wrong codes, **same** IP | 6 wrong tries | keeps accepting attempts past 5 | locked after 5 (423) |
| A' | `POST /v2/auth/otp/verify` | Ben's account, wrong codes, **rotating** IP each try | 6 wrong tries, 6 IPs | every try counted fresh (per-IP resets) | still locked after 5 (challenge-keyed) |
| A'' | `POST /v2/auth/otp/request` | Ben's account after five wrong codes | request replacement before original ten-minute expiry | new challenge issued, budget resets | 423/`locked` until original window ends |
| B | `GET /v2/invoices?email=…` | Alice (Cedar) | 31 same-IP lookups, then 60 rotating-IP lookups in a fresh window | same IP: 31st 429; rotating: all served | 31st 429 in either sequence, keyed by tenant and route |
| C | `GET /v1/invoices?email=…` | Alice (Cedar) | same two sequences as B | all served, including same-IP 31st | 31st 429 in either sequence, keyed by tenant and route |
| D | `GET /v2/invoices?limit=N` | Alice | `limit=1000000`, test-only store with 60 Cedar rows | returns 60 rows | capped at 50 rows |
| D' | `GET /v2/invoices?limit=50` | Alice | send 10,000 times | served (size cap doesn't bound frequency) | served unless a frequency budget is also present — decoy: size cap ≠ rate budget |

Test B and C with independent limiter fixtures so their same-IP 31st requests show opposite
vulnerable outcomes; use a fresh window for the rotating-IP probe. Fixed mode denies the 31st on
both routes. D's 60 rows are test-only fixture data, not new fixed invoice IDs in CONTEXT.
