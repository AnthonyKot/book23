# Brief — Chapter 6, "Every Request Was Valid" (API6: unrestricted access to sensitive business flows)

Status 2026-09-23: incident found and verified against the primary court filing; chapter draft
written at `chapters/06-every-request-was-valid.md`. No service code exists yet for the refund
flow; everything below is the specification for it. The chapter and brief are committed for
the author's read, with implementation still pending.

## Mechanism sentence and class fit

The complaint alleges that between January 2017 and at least February 2019 Just In Time Tickets
ran the Automatick and Tixman bots to search, reserve and buy Ticketmaster tickets through more
than 436 accounts, 450 credit cards and 12,500 IP addresses, making more than 14,186 purchases
for more than 48,451 tickets in excess of posted per-event limits. Individual purchases could
appear ordinary while the sequence evaded a limit keyed on identities the buyer could multiply.
That supports OWASP API6 (excessive use of a sensitive business flow), not a race (no atomicity
failure is alleged) or brute force (nothing was guessed).

Primary sources (fetched, read in full; archive to `resources/incidents/06/`):

- **A.** United States v. Just In Time Tickets, Inc. and Evan Kohanian, Complaint for Permanent
  Injunction and Other Equitable Relief, E.D.N.Y. 21-CV-215, dated 14 Jan 2021 (docket stamp

Caveat the chapter honours: the complaint *alleges*; the order says defendants "neither admit nor
deny". The chapter says "the complaint says" / "the government described" and states the
no-admission settlement. The complaint says "websites", never "API"; the chapter says so
explicitly and claims only that the shape is API6.

Candidates examined and set aside (for the record):

- Homakov / Starbucks gift-card race — atomicity, rejected earlier (CONTEXT).
- NY AG 2017 settlements (Prestige Entertainment, $3.35M; "1,012 tickets to a 2014 U2 concert in

  (IDOR-shaped), not volume of a valid flow.
- Unikrn HackerOne #277407 (referral abuse via email aliases) — closer to API6 scenario 3 but a

## Handlers and mode behaviour needed in `service/`

- `POST /v2/refunds/quote` (both modes): `currentUser` → `LoadInvoiceFor(user, invoice_id)`
  (404 if not the tenant's) → reject `amount > inv.Amount - inv.Refunded` (400) → store
  `Quote{ID, Tenant, InvoiceID, Amount, Status: open}`; first quote for 104 gets `q-771`
  (deterministic id sequence from the store; later ids unnamed).
- `POST /v2/refunds/confirm`:
  - **vulnerable** (`ch06-vulnerable-confirm`): load quote; 404 if `quote.Tenant != caller.Tenant`;
    if already confirmed return the original refund (idempotent); check remaining balance;
    record `Refund{QuoteID, InvoiceID, Tenant, Amount, At}`; mark confirmed. No allowance.
  - **fixed** (`ch06-fixed-confirm`): same, but the record step is `store.ConfirmRefund(quote)`,
    which sums today's refunds for `quote.Tenant` (fake clock) and, if the sum plus this amount
    exceeds the tenant's allowance, sets `quote.Status = needs_approval` and returns a typed
    result the handler encodes as `{"status":"refund_needs_approval"}` (HTTP 202 suggested; the
    chapter names only the body property). Idempotent replay unchanged.
  - **per-user counter** (`ch06-per-user-counter`): the insufficient local fix; needed only as a
    real excerpt. Suggest a third build flag or an unexported helper compiled but wired only in a
    test (`refundedToday(user)`) so the excerpt is real without adding a third Mode. If a third
    mode is unacceptable, the excerpt can be a function in the file that no mode registers, and
    the brief must say the test proves its gap directly by calling it.
- `store.ConfirmRefund` (`ch06-tenant-allowance`): the choke point; takes tenant from the stored
  quote; total computed and refund recorded in one store call (single mutex in the in-memory
  store; no goroutines in tests).
- `POST /v2/refunds/{quote}/approve`: scope before admin role via ch. 5 middleware; Dana approves
  a parked quote and the refund records regardless of the allowance; Alice on a Cedar quote → 403,
  Ben on that quote → 404.
- Callers: Alice session, Dana session, Ben session, `ck_cedar_…` integration key resolving to a
  Cedar service identity (ch. 2 semantics; no `X-User`).
- Velocity signal (quotes per tenant per hour): prose only in this draft; implement as a counter
  Ops can read if cheap, otherwise leave as prose and say so in the test comments.
- Reminder route (exercise E): prose only. If implemented, fixed mode adds a per-invoice per-day
  allowance of one and returns the same needs-a-different-flow shape.

Decoy = exercise A (idempotent confirm). Pair = B (per-user) vs C (per-tenant), one token apart,

proving a vulnerability).
