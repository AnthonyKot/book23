## Mechanism sentence and fit

DPD's tracking page, gated only by parcel code plus a postcode derivable from an unauthenticated
map-image endpoint, drew itself from a JSON response that carried the recipient's contact details
(full name, email, mobile) which the page never displayed — the server sent properties of the
object beyond what the authorised view needed, which is OWASP API3 (excessive data exposure at
the property level); the weak postcode gate is a separate object-level weakness and the chapter
says so.

Primary: David Lodge, Pen Test Partners, "DPD package sniffing", 7 Feb 2022
(https://www.pentestpartners.com/security-blog/dpd-package-sniffing/). Secondary for the field
list: BleepingComputer, 7 Feb 2022.

## Ledger design (proposed; CONTEXT.md additions in bold)

Stored type `store.Invoice`: ID, Tenant, Number, **Amount (104: £1,800.00; 205: £640.00)**,
Currency, Status, DueDate, Reference (PO number, tenant-editable), Customer{Name, Email, Phone,
Address}, **CollectionsNote (Ledger-internal)**, **Margin (Ledger-internal)**.

Views (server-side, built after `LoadInvoiceFor`):
- `InvoiceView` for ordinary tenant users (Alice, Ben): Number, Amount, Currency, Status, DueDate,
  Reference, Customer.Name.
- `InvoiceAdminView` for tenant admins (Dana): + Customer.Email/Phone/Address.
- CollectionsNote and Margin: never encoded on any customer-facing route.

Write side: `InvoicePatch{Reference}` is the only decodable request type for tenant users.
Vulnerable mode decodes the body straight into the loaded `store.Invoice` (Status, Amount, Tenant
settable). `PATCH /v2/users/me` vulnerable mode decodes into `User` including `IsAdmin` (Alice
promotes herself); fixed mode decodes `ProfilePatch{DisplayName}`.

Enforcement idea for the choke point: `store.Invoice` gets a `MarshalJSON` that returns an error
("encode a view, not the row"), so any handler that encodes the stored type fails its own test.

## Handlers needed

| Route | Vulnerable | Fixed |
|---|---|---|
| `GET /v2/invoices/{id}` | Encode(inv) | Encode(ViewFor(user, inv)) |
| `GET /v2/me/invoices` | Encode([]store.Invoice) | Encode([]InvoiceView) |
| `GET /v1/invoices/{id}/pdf` | template prints Customer.Email/Phone | template bound to InvoiceView |
| `PATCH /v2/invoices/{id}` | decode into inv, save | decode InvoicePatch, apply Reference only |
| `PATCH /v2/users/me` | decode into User (IsAdmin) | decode ProfilePatch |

## Exercise-case matrix (proposed)

| Case | Route / handler shape | Caller | Request | Vulnerable | Fixed |
|---|---|---|---|---|---|
| A | `GET /v2/invoices/{id}` → ViewFor | Alice | 104 | body has `customer.email`, `margin` | body lacks `customer.email`, `collections_note`, `margin`; has `amount` |
| B (decoy: looks like the leak, is fixed) | `GET /v2/me/invoices` → loop ViewFor | Alice | — | rows carry `margin` | rows lack `margin`/`customer.email` |
| C | `GET /v1/invoices/{id}/pdf` | Alice | 104 | PDF text contains customer phone | PDF lacks phone/email |
| D (pair, safe) | `PATCH /v2/invoices/{id}` decode `InvoicePatch` | Alice | `{"reference":"PO-9","status":"paid"}` | — | reference updated, status unchanged |
| E (pair, vulnerable) | `PATCH /v2/invoices/{id}` decode `map[string]any`, set each key | Alice | `{"status":"paid","amount":0}` | status=paid, amount=0 | rejected / only reference applied |
| F | `PATCH /v2/users/me` | Alice | `{"is_admin":true}` | Alice becomes admin; `GET /v2/invoices/104` now shows email | field ignored, 4xx or unchanged |
