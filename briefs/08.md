# Brief — Chapter 8, "Left On" (API8 security misconfiguration)

Status 2026-09-23: **incident CHOSEN — UpGuard's Microsoft Power Apps portals disclosure (2021)**;
both register pointers rejected on their own records (below). `chapters/08-left-on.md` drafted,
~2,180 words counting the exercise table (~2,050 prose). No service code for this chapter exists;
everything below is its specification for Lane A.

## 1. Mechanism sentence and class fit

Power Apps portals exposed each list through an OData API at `/_odata/<list>`, and a list's rows
were readable anonymously whenever the OData feed was on and the list's "Enable Table
Permissions" Boolean was not set — a setting that was off by default on every list, so that the
table permissions (present, correct, enforced on everything else) were simply ignored — which is
OWASP API8 security misconfiguration (an unsafe default / unnecessary feature enabled), not a
missing authorization check (the check existed and worked once the setting was on) and not a
forgotten host (the portals were meant to be public; the lists were not).

Primary source (fetched, read in full; archive to `resources/incidents/08/`):
UpGuard, "By Design: How Default Permissions on Microsoft Power Apps Exposed Millions",
23 Aug 2021, https://www.upguard.com/breaches/power-apps. Class definition:
https://api-security.owasp.org/editions/2023/en/0xa8-security-misconfiguration/ (not re-fetched
this session; wording in the chapter is generic).

Fit notes the chapter honours: UpGuard "understand (and agree with) Microsoft's position that the
issue here is not strictly a software vulnerability" — the chapter says so and uses it as the
class argument. Microsoft is named because UpGuard names it; the notified organisations are not
named in prose except Microsoft's own payroll portal. The 38 million / 47 entities / "over a
thousand lists across a few hundred portals" figures are UpGuard's own totals.

## 2. Rejected pointers

- **All in One SEO (Domoney case 6), CVE-2021-25036.** Primary: Jetpack/Automattic (Marc Montpas),
  "Severe Vulnerabilities Fixed in All In One SEO Plugin Version 4.1.5.3", Dec 2021,
  https://jetpack.com/blog/severe-vulnerabilities-fixed-in-all-in-one-seo-plugin-version-4-1-5-3/.
  Mechanism: `Api::validateAccess()` compared the requested REST route case-sensitively while
  WordPress matches routes case-insensitively, so one uppercased character skipped the privilege
  check; a subscriber then reached `aioseo/v1/htaccess`. That is an authorization-bypass bug in
  code (API5 by shape, ch. 5 territory; PLAN §3 row 8's "case-insensitive path bypass" belongs
  with it), not a setting left on. Rejected for API8.
- **Home router (Domoney case 8).** Domoney's own root-cause line: "a case of broken
  authentication, where an exposed API endpoint allowed access without authentication", plus OS
  command injection on `/cgi-bin/adm.cgi`; no vendor or CVE named in the book. A web search for
  the endpoint did not identify the primary write-up. Rejected on Domoney's retelling alone: API2
  plus injection, nothing configured.
- Considered and not pursued: James Kettle's CORS write-up (PortSwigger 2016) — good API8 but
  Ledger uses bearer tokens, not cookies, so a CORS story would not survive its own mechanism on
  Ledger; Spring Boot actuator disclosures — many, none with a single clean primary record and
  numbers.

## 3. Ledger design

### Objects reused
Route table with `Access` levels `Public` / `User` / `TenantAdmin`, the middleware after
`currentUser`, and the "every route declares" test (ch. 5) — the primary bug is a wrong *value*
in that table. `LoadInvoiceFor` and the 404-for-forbidden decision (ch. 1) — the second path
undoes its effect through a setting. Alice (Cedar), Dana (Cedar admin), invoice 205 (Birch),
hosts `api.ledger.example` and `ledger-staging.internal` (ch. 9's object, mentioned as existing
and still configured — consistent with ch. 8 preceding ch. 9's retirement; the ch. 9 fixed
state must not be contradicted: in a cumulative post-ch. 9 build the staging host would simply
be absent from `Settings.Hosts`). `POST /v2/auth/otp/request` and `POST /v2/auth/otp/verify`
(ch. 4) as the only legitimately `Public` routes besides the probe. Ops as gateway owner.

### The bug (a setting, not a check)
`GET /v2/health` — `Public`, body `{"ok":true}` (correct; the decoy). `GET /v2/admin/health` —
copied from it, declared `Public`, body `{version, commit, hosts:[api.ledger.example,
ledger-staging.internal], debug:true}`. The ch. 5 declaration test passes (the route has a
level). Values in prose are `"version":"…"` — no version number is ever given, to avoid
look-alike numbers.

### Second path (reuses ch. 1's repair inside the worked example)
`Settings.Debug` left on from staging. The error writer appends `reason` to invoice error bodies
when `Debug` is true, so Alice's `GET /v2/invoices/205` still gets 404 but with
`{"error":"not found","reason":"invoice 205 belongs to tenant birch"}`. The loader is untouched;
the setting leaks its verdict. Chapter 1's `LoadInvoiceFor(user,id)` still returns only
`(Invoice,bool)`: an unexported store helper `invoiceMissReason(user,id)` looks up the stored
tenant only after that loader has denied the request and only when vulnerable `Debug` is true.
It returns a generic reason for a missing invoice. The fixed error writer never calls it or
includes its result; handlers still cannot call bare `store.Invoice(id)`.

### Repair: configuration as code
- `Settings` struct (`ch08-production-settings`): `Debug bool`, `CORSOrigins []string`
  (production: Ledger's own web-app origin only; exact origin string is an implementation
  choice — suggest `https://app.ledger.example`, and record it in CONTEXT if adopted),
  `PublicRoutes []RouteKey` (method and pattern only: `GET /v2/health`, `POST /v2/auth/otp/request`,
  `POST /v2/auth/otp/verify`),
  `Hosts []string`. Two literals: `ProductionSettings()` and `StagingSettings()`; no inheritance.
- Settings test (`ch08-settings-test`): walks `Routes()` and fails on any route with
  `Access == Public` not in `PublicRoutes`; asserts `Debug == false`; asserts no origin is `*`;
  sends Alice→205 in fixed mode and asserts the body is exactly `{"error":"not found"}`.
- Fixed declaration (`ch08-fixed-health-decl`): `GET /v2/admin/health` → `TenantAdmin`, body
  `{"version":"…"}` only; hosts and debug flag removed from the response, not gated.
- Mode behaviour: **vulnerable** = table entry `Public`, `Debug: true` in the served settings,
  error writer appends reason. **fixed** = entry `TenantAdmin`, `ProductionSettings()`,
  error writer omits reason. The settings test is a build-time assertion: factor a
  `validateProductionSettings(settings,routes) error` helper and assert that the fixed settings
  pass while a copy with `Debug:true` returns a validation error. Do not run an intentionally
  failing Go test as evidence of the vulnerability. Both-mode HTTP cases assert served responses.

### Handlers needed
`GET /v2/health` (both modes, `Public`); `GET /v2/admin/health` (declaration differs by mode;
body differs by mode); error writer with `Debug` branch (`ch08-debug-error-writer`), used by
the ch. 1 invoice handler's not-found path and supplied the denial reason by
`store.invoiceMissReason` only in vulnerable mode; `Settings` plumbing into `NewApp`.
