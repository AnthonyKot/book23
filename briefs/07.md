# Brief — Chapter 7, "The Server That Fetched for You" (API7 SSRF)

Written 2026-09-23. ~1,770 words of prose.

## Mechanism sentence and class fit

Shopify Exchange's create-a-listing flow rendered a screenshot of a seller-controlled store, and
because the seller could make that store's template redirect the browser (`window.location`) to the
cloud metadata service (`metadata.google.internal /computeMetadata/v1beta1/...`, whose `/v1beta1`
path returned the instance service-account token without the `Metadata-Flavor` header), the
screenshot browser followed that script navigation and painted the token into the listing PNG — the server was
made to issue an outbound request to a destination the caller influenced and reached an internal
address the caller could not reach directly, which is OWASP API7 (server-side request forgery).

Surface difference (stated in the chapter): Exchange's surface is a headless-browser screenshot
renderer driven by a page the seller controls and a client-side redirect; Ledger's is a webhook
"test" route that fetches a URL the caller submits directly. Same class, different entry.

Primary source: HackerOne report #341876, https://hackerone.com/reports/341876 (fetched and read as
JSON; reporter 0xacb, submitted 2018-04-22, disclosed 2018-05-23, weakness SSRF, scope
exchangemarketplace.com). Corroboration/fix wording: Shopify team summary on that report, and
Shopify, "One Million Dollars in Bug Bounties", 3 Apr 2019,
https://shopify.engineering/blogs/engineering/one-million-dollars-in-bug-bounties (article date
confirmed; the .../engineering/... URL 301-redirects to shopify.engineering). Domoney case is the
pointer only.

## Handlers / functions needed in `service/`

- `POST /v2/webhooks/test` — **vulnerable** (`ch07-webhook-vulnerable`): parses URL, requires
  `https`, rejects the literal `http://169.254.169.254/`, then calls an injected `*http.Client`
  configured with `http.Get`'s default resolve, dial and redirect behavior. Production uses the
  default client; tests inject a fixture client. Returns the destination status.
- `egress` outbound client (`ch07-egress-policy`): resolve hostname once → reject loopback,
  link-local (169.254.0.0/16, ::1, fe80::/10), RFC1918/ULA private and special-use ranges,
  including RFC5737 documentation ranges → dial the *approved* address (pinned via a custom
  `DialContext`, with the original hostname retained for HTTPS server-name validation and no
  environment proxy) → `CheckRedirect` returns `http.ErrUseLastResponse` (redirect returned,
  not followed). Reject a hostname if any resolved address is disallowed.
- `POST /v2/webhooks/test` — **fixed** (`ch07-webhook-fixed`): identical logic, calls `egress`
  instead of `http.Get`.
- PDF logo fetch (`ch07-pdf-logo-fetch`): the `/v1/invoices/{id}/pdf` renderer fetches
  `tenant.Branding.LogoURL` through `egress`; vulnerable mode uses the injectable default-behavior
  client. Both modes retain `LoadInvoiceFor` before rendering, as Chapter 1 requires.
- Mode behaviour: vulnerable mode dials DNS answer and follows redirects; fixed mode enforces the
  egress policy on both the webhook test and the logo fetch. Fixed mode keeps all earlier repairs.

## Test injection (network-free, deterministic)

- Fake resolver: a `map[string][]net.IP` used by the fixed egress policy and by the vulnerable
  client's injected dialer. It points `hooks.cedar.example` at either public `8.8.8.8` or
  link-local `169.254.169.254`, and `report.cedar.example` at public `1.1.1.1`.
- Separate network-free fixtures test separate properties: a fake `DialContext` records the
  host:port it was asked to dial (and returns a sentinel error), proving vulnerable case 3
  attempts the link-local address and fixed mode refuses before dialing; a canned
  `http.RoundTripper` returns 200 or 302 responses for cases 2, 4 and 5. The round-tripper alone
  cannot prove pinning, so add a direct egress dial-callback test that asserts the approved IP
  rather than a second hostname resolution. Production uses `net.Dialer.DialContext`.
- The fixture's public IPs are address-class test values only. No socket connects to them; the
  canned transport models successful HTTPS responses without relying on live certificates.
- No real time, no network, no goroutines.

## Exercise-case matrix (→ service/ch07_test.go, both modes)

Route `POST /v2/webhooks/test`, body `{url}`. "Blocklist" = a teammate's proposed fix (reject host
== 169.254.169.254 or metadata.google.internal); the chapter uses it only as the decoy's framing;
`egress` is the real fix under test.

| Case | url | DNS answer | destination reply | Vulnerable build | Fixed (egress) build |
|---|---|---|---|---|---|
| 1 (decoy) | `http://169.254.169.254/latest/meta-data/` | literal IP | 200 token if fetched | rejected before fetch by HTTPS requirement | rejected before fetch |
| 2 (baseline) | `https://hooks.cedar.example/ledger` | 8.8.8.8 (public test value) | 200 "ok" | fetched, 200 | fetched, 200 |
| 3 | `https://hooks.cedar.example/ledger` | 169.254.169.254 | HTTPS reply not guaranteed | attempts link-local dial; token leak not asserted | refused before dial |
| 4 (pair-vuln) | `https://report.cedar.example/hook` | 1.1.1.1 (public test value) | 302 → `http://169.254.169.254/` | follows redirect, fetches metadata in fixture | redirect not followed; no internal fetch |
| 5 (pair-safe) | `https://report.cedar.example/hook` | 1.1.1.1 (public test value) | 200 "ok" | fetched, 200 | fetched, 200 |

- Decoy: case 1 (the request an attacker would never send; blocklist "works" only here).
- Near-identical pair with opposite outcomes: 4 vs 5 — byte-identical submission, opposite result in
  vulnerable mode; the discriminator is redirect-following, which happens after any URL check. Fixed
  mode collapses both to the public host.
- Case 3 is the DNS-rebinding illustration (name-based allow-list defeated).

Second-path test (not in the printed exercise, but in ch07_test.go): rendering
`/v1/invoices/{id}/pdf` with `tenant.Branding.LogoURL` at a synthetic public HTTPS host that
returns a 302 to HTTP metadata reaches that address in vulnerable mode, but stops at the redirect in
fixed mode. Also test a logo host resolving link-local: vulnerable mode attempts the dial, fixed
mode refuses before dial. Keep the Chapter 1 `LoadInvoiceFor` two-user test on the PDF path.

Verify.sh note: case 1 asserts refusal in both modes; case 3 asserts attempted link-local dial
versus pre-dial refusal; case 4 asserts a redirect-following internal fetch only in vulnerable mode. Cases
2/5 assert the legitimate fetch still succeeds in BOTH modes. Comment these distinct outcomes in
the tests so a failed HTTPS handshake is not mistaken for proof of a token leak.
