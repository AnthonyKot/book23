## Chapter 04 — Nobody Counted

Mechanism: Muthiyah found that Instagram's six-digit mobile recovery code could be guessed at
scale by combining IP rotation with concurrent requests despite observed rate limiting. This
supports API4's resource/attempt-budget lesson, but the source does not prove the exact server
key or that IP rotation alone was the only bypass.

Findings before edits:

- **BLOCK:** The brief leaves the fixed lookup routes with the same IP-keyed or absent budget it
  criticizes, and its B/C rows intentionally pass in both modes. That cannot satisfy the book's
  both-mode exercise contract or give Lane A a completed fixed behavior. The chapter also calls
  A/B near-identical although the lookalike lookup pair is B/C; it never probes the 31st request
  from one IP that makes B/C visibly different.
- **BLOCK:** Locking one OTP challenge after five failures is bypassable if
  `POST /v2/auth/otp/request` immediately issues a fresh challenge with a fresh budget. The
  chapter says a new code must be requested but neither chapter nor brief limits that reset.
  Lane A needs the request route's locked-window behavior specified.
- **FIX:** The primary article names both a race hazard and IP rotation. It reports about 250 of
  1,000 requests passing and roughly 200 per IP in one test, not a verified exact per-IP-only
  limiter implementation. Narrow the causal claim to the observed bypass.
- **FIX:** HackerOne #1439026 is a discoverability restriction bypass. It does not document the
  login page's rate limit or a missing lookup rate limit, so the Twitter aside cannot state either
  as fact. X's own update supports the later 5.4-million set and its July sale report, with
  careful attribution; use that instead of merging a source reporter's risk with observed scale.
- **FIX:** The `limit=1000000` example cannot make Ledger's two-row fixture return a million
  rows. State the possible work on a larger store, not a current fixture outcome.
- **NOTE:** Ledger reuses the still-serving `/v1` and Chapter 1's shared-route lesson; the hinge
  is “Finding every door is step one either way.” D is a plausible partial-fix decoy. A reader
  can identify the target-versus-IP check, but the brief currently asks Lane A to preserve the
  flaw in both modes, obscuring what should improve.

Design answers before edits: **visible pair — no** for the printed A/B claim; B/C become a useful
pair only with a same-IP sequence. **Lane A ready — no:** fixed lookup budget key/route coverage
and OTP reissue semantics are missing. **State of Ledger — partly:** the 5-attempt, 50-item and
30/min numbers agree, but the proposed fixed service leaves `/v1` uncounted despite the table's
post-Chapter-4 lookup budget.

Changed: `chapters/04-nobody-counted.md` now attributes both concurrency and IP rotation to the
researcher, removes unsupported Twitter rate-limit claims, qualifies the large-page example,
and makes B/C the same-IP 31st-request pair. It says a locked OTP target cannot reset its five
attempts by immediately requesting a new challenge. `briefs/04.md` specifies that reissue rule,
a fixed 30/min tenant-and-route budget on both v1 and v2, fresh limiter fixtures for the B/C
pair, and 60 test-only Cedar rows so the page cap has a visible result. `CONTEXT.md` records the
ten-minute challenge window as a new fixed value. Four primary-source files and ten located
claim rows were added under `resources/incidents/04/` and `checks/claims/04.tsv`.

Design answers after edits: **visible pair — yes**, B and C have opposite outcomes on the 31st
same-IP lookup before the repair. **Lane A ready — yes for the specified cases**, including OTP
reissue and the 60-row page fixture; it must implement and test both modes rather than infer
them from this review. **State of Ledger — yes:** existing 5, 50 and 30 limits are unchanged,
the ten-minute window is newly registered, and the fixed v1 lookup is counted.

Validation: the claims ledger has ten seven-column rows with existing archives; `go test ./...`
from `service/`, `./verify.sh` and `git diff --check` passed. `verify.sh` checked the currently
rendered 11 chapter pages and reported 31 pending code blocks; it did not test Chapter 4 or
rebuild the site from the edited Markdown.

Left for the author and Lane A: implement the Chapter 4 routes, fake clock and limiter fixtures,
then assert every exercise outcome in vulnerable and fixed modes. The Instagram disclosure also
used concurrency, which this deterministic lesson deliberately does not simulate.

Verdict: **ready for the author's prose read, not yet executable**. The decisive remaining gap is
the absent Chapter 4 service and both-mode tests.

## Chapter 05 — Same Door, Different Verb

Mechanism: Zveare's DEF CON deck shows an account with a valid session but no admin permission
reaching the dealer portal's create-user API after a browser-only access check was bypassed; the
API checked the session, not the admin role. This directly supports the book's API5 classification,
although the researcher's own label was broader “authentication.”

Findings before edits:

- **BLOCK:** The vulnerable-mode prefix guard described in the brief would deny Alice on
  `/v2/admin/users` and `/v2/admin/users/{id}`, contradicting the chapter's central D/E outcomes.
  Its F row says 200/403, while the chapter correctly reasons that Go's exact route matching
  yields 404/404 for `/v2/Admin/users`. Keep the observed server gap and remove the fictional
  prefix guard from this chapter's build contract; a later Chapter 8 dependency on that guard
  will need redesign outside this pass.
- **BLOCK:** State of Ledger says invoice tenant scope runs before role checks. The draft instead
  puts role middleware before a handler-local `LoadInvoiceFor`, so its claim that Dana's
  cross-tenant delete returns 404 *before* the role check cannot be true under the described
  chain. Lane A needs an explicit pre-handler scope stage for ID routes or a documented change to
  the state table; this review should preserve the table.
- **FIX:** The archived primary deck is a 77-slide “Unexpected Connections” presentation dated
  10 August 2025, not the Chapter 5 header's purported 8 August slide deck. Its exact slide
  locators differ. Correct the source credit and use those locators in the claims ledger.
- **FIX:** The slides show a profile-update step establishing a usable session after the
  no-permission account was registered. The chapter currently skips that necessary link. It also
  presents a later impersonation pivot as if it were part of the initial national-admin function.
- **FIX:** TechCrunch reports Zveare saying the vendor found no prior exploitation, not a direct
  carmaker statement. “Within a week” is tighter than its “about a week” and the deck's
  3 February report / 11 February verified-fix dates.
- **FIX:** A missing access declaration is a registration or test failure in the proposed Go
  service, not a compile-time guarantee. The F answer's hypothetical case-folding router is not
  needed to explain the registered-route check.
- **NOTE:** The Ledger example depends on the Chapter 1 loader, Chapter 3 typed profile patch,
  invoice 104 and Alice/Dana roles. Its hinge is “make every route state, in one place, who may
  call it.” A is a plausible safe-write decoy; B/B' give opposite fixed outcomes for the same
  delete route with a different caller, and E/E' show a route-level privilege difference. A cold
  Go reader can trace the role to 403 once middleware and scope ordering are explicit.

Design answers before edits: **visible pair — yes** for B/B' and vulnerable E/E', but F's brief
outcome is impossible under the named router. **Lane A ready — no:** prefix enforcement and
scope/role ordering are contradictory. **State of Ledger — no:** the chapter says handler-local
scope after role middleware even though the state table requires scope first.

Changed: `chapters/05-same-door-different-verb.md` now cites the archived August 10 slide deck,
adds the profile-update session step, separates national-admin creation from later impersonation,
attributes the no-prior-exploitation statement to Zveare, and specifies invoice scope before the
role stage. Its F answer is 404 in both modes under the named Go router. `briefs/05.md` now gives
Lane A one scope → role → handler chain, drops the contradictory vulnerable prefix guard, aligns
F with the chapter, and corrects slide locators. The primary deck and researcher interview are
archived with two manifest rows and eleven located claims in `checks/claims/05.tsv`.

Design answers after edits: **visible pair — yes**, B/B' differ by caller role on the same delete
route in fixed mode, while E/E' differ by route in vulnerable mode; A remains the plausible safe
write decoy. **Lane A ready — yes for this chapter's specified paths:** the scope/role order,
status and state effects are explicit. **State of Ledger — yes:** invoice and target-user tenant
scope run before access checks, with 404 for a foreign target and 403 for insufficient role on a
same-tenant target. Chapter 8's planned prefix-bypass dependency no longer follows from this
chapter and must be revised when Chapter 8 is in scope.

Validation: the claims ledger has eleven seven-column rows with existing archives; `go test ./...`

existing Chapter 1/9 Go cases and currently rendered site pages, not Chapter 5's proposed paths.

Left for the author and Lane A: implement the scope stage, access declarations and both-mode
exercise tests; when reviewing Chapter 8, replace its presumed prefix guard with an actual

Verdict: **ready for the author's prose read, not yet executable**. The main remaining gap is the
unbuilt Chapter 5 service and tests; the downstream Chapter 8 dependency is a separate later
design task.

## Chapter 06 — Every Request Was Valid

Mechanism: the FTC complaint alleges that Just In Time Tickets used ticket bots, many accounts,
cards, identities and proxy IPs to evade Ticketmaster's per-event purchase controls. This is a
strong API6 analogue for a sequence-level business limit, while the filing describes a website,
not an API vulnerability.

Findings before edits:

- **BLOCK:** The exercise asks for fifty fresh £400 refunds on invoice 104, which contains only
  £1,800. Confirm's remaining-balance check stops the fifth refund, so the claimed fifty-refund
  outcomes cannot occur in either build. B/C must use the seeded £1,000 tenant total and one
  further £400 request, while A can use three fresh quotes to expose the allowance gap.
- **BLOCK:** The chapter and brief say Alice receives 404 on the admin approval route. Chapter 5's
  State of Ledger contract gives 403 for a same-tenant caller with insufficient role, after scope
  passes. This is a direct contradiction Lane A would otherwise implement.
- **FIX:** The complaint alleges circumvention of purchase controls; it does not establish that
  every ticket was paid for, each account stayed under its individual limit, or the flow was
  “used exactly as designed.” Qualify the incident as allegations about a valid-looking sequence.
- **FIX:** The chapter calls the daily allowance a tenant rule, but says the web UI greys out
  Alice's button based on “the day's refunds” without naming the tenant scope. State it explicitly.
- **NOTE:** The Ledger example reuses invoice 104, q-771, LoadInvoiceFor, the integration key and
  the Chapter 5 role check. Its hinge is “Nothing asks what the tenant has already refunded
  today.” D is a plausible false-positive decoy; B/C can be a visible per-user/per-tenant pair
  once the sequence is bounded by the actual invoice balance.

Design answers before edits: **visible pair — no** for the printed fifty-refund outcome because
the invoice balance stops it; **Lane A ready — no** because the exercise and matrix contradict
the balance and Chapter 5 role status; **State of Ledger — no** because same-tenant wrong-role
approval is 403, not 404.

Changed: `chapters/06-every-request-was-valid.md` now treats the FTC account as allegations,
removes unsupported “every ticket paid” and per-account-limit assertions, gives A three fresh
£400 quotes, and tests B/C with one £400 request after Cedar's £1,000 total. The approved-route
answer is 403 for Alice's same-tenant quote. `briefs/06.md` gives Lane A that same scope-then-role
outcome, including Ben's cross-tenant 404. The three FTC primary records are archived with nine
located claims in `checks/claims/06.tsv`.

Design answers after edits: **visible pair — yes**, the same integration-key request passes B's
per-user counter but parks the quote under C's tenant counter, while invoice 104 has enough
remaining balance for the contrast. **Lane A ready — yes for the stated refund paths**, subject
to implementation and both-mode tests; **State of Ledger — yes**, same-tenant wrong-role is 403
after scope and cross-tenant is 404.

Left for the author and Lane A: implement the refund store, quote and approval routes and prove
the sequences in both modes. The reminder route remains an exercise-only second flow, as the
brief already states, so its E outcome is not executable yet.

Validation: nine seven-column claim rows point to existing archives; `go test ./...`,
`./verify.sh`, and `git diff --check` passed. The verifier checks the existing Chapter 1/9 Go
tests and reports 31 pending code blocks; it does not execute Chapter 6's refund sequences.

Verdict: **ready for the author's prose read, not yet executable**. The main remaining gap is the
unbuilt refund flow and its both-mode sequence tests.
